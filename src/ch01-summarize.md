## 1.1 什么是 AI Agent

### 1.1.1 先从一个生活问题开始：会回答，不等于能办事

想象这么一个场景，你要规划一次国庆长假出游，于是你去请教一位旅行达人：

> "我想国庆做一次长途旅行，预算 10000元，最好适合带老人孩子，请你帮我推荐一些合适的旅游线路和景点。"

这位旅行达人会基于他自己以往的经验，给你一份看起来看不错的旅行建议：

- 他会推荐经典的路线和热门的景区
- 他会帮你评估预算并列出行李清单
- 他甚至会告诉你很多鲜为人知的风景秘境与避坑指南

但是他没法帮你查询和订阅车票，没法帮你确认酒店是否有空房，也没法核对了景点的开放时间，更不会自动替你把信息整理到日历里。



那么再想象一下，如果你有一位非常聪明的生活助理小姐姐，针对同一个旅行行程规划的要求，她可能会：

- 首先确认出发城市、日期和老人、孩子年龄
- 再查询天气、交通和住宿，并比较价格与距离
- 发现某家酒店超预算后她会换一个选项
- 最后把行程、费用、预订链接和待确认事项整理出来
- 涉及付款或不可撤销的预订时，它会征得你的同意后再执行



上面第一个例子中的旅行达人，就是我们今天提到的**大语言模型 LLM （Large Language Model）**；

而第二个例子中的生活助理小姐姐（也许还是一位非常漂亮的小姐姐）就是我们所说的 **AI Agent（人工智能智能体，简称Agent）**。

它们二者最重要的区别不是"答案写得更长"，而是能否围绕一个目标，持续地判断下一步要做什么、调用合适的能力、观察执行结果，并根据结果调整行动。

我们可以进一步画出一个表格，针对规划旅行线路这个目标，看看单纯的大模型和 agent 分别都能为我们做点什么：

|                                      | 旅游达人（LLM） | 生活助理（AI Agent） |
| ------------------------------------ | --------------- | -------------------- |
| 规划线路与景点（思考规划）           | ✅               | ✅                    |
| 查询天气、交通及住宿（感知环境）     | ❌               | ✅                    |
| 订阅车票、门票与酒店（调用工具执行） | ❌               | ✅                    |
| 订阅失败后的补救措施（反思、修正）   | ❌               | ✅                    |

> 有老师提到，当前很多新版的模型自身已经具备了反思的能力，这点说的很对！但是这里提到的反思和修正是指 agent 调用工具执行并观察到失败的结果后，再次发起的反思和补救措施。



所以基于以上的比较，我们是否可以先得到一个关于 AI Agent 的定义

> **AI Agent = LLM + 环境感知 + 工具调用 + 反思/修正**



如果再次观察上面的公式，我们发现，“反思”其实是观察上一次工具调用的输出结果是否符合预期，其实也是属于“环境感知”的范畴；而“修正”就是再一次的“工具调用”。

那么上面关于 AI Agent 定义的公式可以进一步简化为：

> **AI Agent = LLM + 环境感知 + 工具调用**

**请记住上面这个公式吧！这是对 AI Agent 最朴素的定义！**



比如我们平时提到的 DeepSeek-v4、GPT-5.6、Claude-opus5.5 等，通常就是指的 LLM 大模型本身；而支持你输入问题的 claude code、codex、WorkBuddy 以及Cursor，就是我们说的 Agent。



不过需要说明的是：这不是所有研究者都采用的唯一正式定义。不同产品会把"Agent"用在不同范围上：有的指具有较高自主性的系统，有的也把按固定流程运行的智能应用称为 Agent。学习时，与其纠结名字，不如先看系统到底能做什么、由谁决定下一步，以及它能否根据执行结果改变路线。



### 1.1.2 大语言模型是什么？它为什么能成为 Agent 的核心？

今天几乎所有的 Agent 都以 **大语言模型（Large Language Model，LLM）**为核心。可以先把大语言模型理解成一种通过大量文本和其他数据训练出来的通用语言与推理引擎。它能够：

- 理解你提出的问题
- 总结你给出的信息
- 根据具体要求生成文字、写代码
- 也能根据上下文提出下一步行动的候选方案



但是这里有一个非常常见误解：模型既然能回答问题，那么它肯定"知道"答案。

实际上，模型生成的内容是基于训练和当前输入计算出来的输出。它可能掌握某些规律，也可能缺少最新信息、误解问题，甚至用很肯定的语气给出错误内容。因此，模型的回答不能自动等同于事实，更不能自动等同于已经完成的现实操作。

至于大模型为什么能够知道那么多事情，它又是基于什么原理能够给出用户建议和规划，这部分内容我们会在后面详细讲解。



**再举一个生活化的例子：**
你问朋友"这家餐厅今天营业吗？"朋友可能凭记忆回答"应该营业"。如果他真的打开餐厅的官方页面或打电话确认，证据就更充分。

LLM的内部知识类就似"凭已有印象作答"；而Agent则会调用搜索、数据库或业务系统，则更像"去查证"。

LLM 在 Agent 中通常承担如下几类工作：

-   **理解目标**：把用户的自然语言要求转化成可处理的任务。
-   **判断与选择**：分析当前信息，选择下一步行动。
-   **生成结构化指令**：例如生成搜索关键词、工具参数、代码或待办清单。
-   **解释结果**：阅读工具返回的信息，向用户说明发生了什么。
-   **必要时修正路线**：如果查不到资料、工具报错或发现条件不满足，决定重试、换方法或向用户提问。

但要记住的是，在 Agent 系统中模型绝不是全部。一个人即使再聪明、再博学，也需要电话、电脑、钥匙、日历和工作场所才能完成现实任务。类似地，Agent
也需要模型之外的感知系统、工具执行系统和管理机制。



### 1.1.3 一个 Agent 通常由哪些部分组成？

没有一种适用于所有 Agent 的唯一结构图。也没有一种适用于所有业务场景的 Agent。

不同任务需要不同的组件。不过，初学者可以先使用下面这个通用架构理解大多数系统。



![image-20261010183448316](/Users/zhongjywork/Library/Application Support/typora-user-images/image-20261010183448316.png)



这张图是概念模型，不是说所有产品都必须把代码拆成几个独立模块。有些功能可能由一个框架统一提供，有些系统则会把它们拆成多个服务。

#### 组成部分一：模型------负责理解与判断的"大脑"

模型负责理解用户意图、分析可用信息，并提出下一步行动。它可以是云端模型，也可以是部署在本地或私有环境中的模型；可以是通用模型，也可以是针对特定任务优化的模型。

**生活例子：**
在一家旅行社里，模型像熟悉旅游规划的顾问。它能听懂"别太累、适合孩子、预算有限"的意思，并比较不同方案的利弊。

**为什么不能只有模型？**
顾问可能知道如何规划，却不一定能看到实时票价，也不能凭空知道酒店是否还有房间。模型的知识、工具权限和现实世界的状态是不同的东西。



#### 组成部分二：指令与目标------告诉系统要完成什么

Agent 需要知道任务目标、限制条件和成功标准。目标越模糊，系统越可能走偏。指令通常会包括角色、任务、约束、输出要求，以及必要的安全规则。

**生活例子：**
"帮我找酒店"太宽泛；"帮我找周六入住、周日退房、离地铁站步行 10 分钟内、总价不超过 1000 元且可免费取消的酒店"就更容易执行。

好的目标还应该能被检查。比如"让用户满意"不容易直接验证；"列出三家符合预算的酒店，并为每家提供总价、位置、取消政策和来源链接"就更具体。



#### 组成部分三：上下文与状态------让系统记得当前任务进行到哪里

**上下文（Context）**是模型在当前一步能够看到的信息，例如用户的要求、之前的对话、检索到的资料、工具返回结果和规则。

**状态（State）**则强调任务在执行过程中的当前情况，例如已经完成哪些步骤、有哪些待办事项、预算还剩多少、是否已经得到用户确认。

二者相关，但不完全相同：上下文是模型此刻能看到的材料；状态是系统对任务进展的表示。状态可能只把必要部分放进模型上下文，也可能存储在外部系统里。



**生活例子：** 你和旅行社的顾问讨论旅行方案，需要经过多次的沟通。也许每次遇到的并不是同一个顾问。即使是同一个顾问她也有可能将你的信息与其他顾客的信息记混。所以你们在沟通的时候，需要提及之前沟通的情况以及已经达成的合意。

大模型也是一样，LLM 的服务是**无状态的**，也就是说每一次与大模型的对话，都是独立的，与其他对话无任何关系。

上下文和状态的管理，就是让 Agent 能在之前对话的基础上继续工作，让大模型能够“回忆起”前面讨论过的内容。

后续章节会分别深入讨论上下文工程、用户记忆与知识库。这里先记住：**模型能否使用信息，不只取决于信息是否存在，还取决于系统是否在合适的时机把正确的信息提供给它。**



#### 组成部分四：工具（Tools）------让系统能够采取行动

工具是模型之外、人为给 Agent 赋予的具体能力。例如网页搜索、读取文件、查询订单、执行代码、访问数据库、发送邮件或调用网络服务 API 等。

实际上模型没有能力直接操作任何系统和工具（它只能生成字符），模型对于工具的使用方式是提出一个结构化的工具调用请求，并将这个请求作为一次回答给到 Agent，Agent 接收到这个工具的调用请求后，在运行环境中去实际去检查参数与权限，再执行工具，最后把工具执行结果作为下一轮对话的内容再次提交给模型。

**生活例子：**
模型像会做计划的助理，搜索工具像浏览器，日历工具像日程本，订票 API 像售票窗口。助理可以决定什么时候查票，但真正的余票信息来自售票系统。

这里需要强调的是，工具调用不保证一定能成功。模型可能给出错误参数，网络可能超时，服务可能拒绝请求，或者工具执行成功但返回的结果不符合预期。因此，Agent 还需要检查工具结果，并在必要时做出调整。



#### 组成部分五：控制循环（Control Loop）------决定下一步做什么

在绝大多数情况下，Agent 并不是"模型回答一次就结束"，而是按循环推进：

1.  读取当前目标、上下文和状态。
2.  让模型判断下一步行动。
3.  如果需要，调用工具。
4.  观察工具结果或环境变化。
5.  更新状态，再判断是否继续。
6.  达到完成条件、遇到限制或需要用户决策时结束。

**生活例子：**
你烤蛋糕时先按食谱设定时间，再观察蛋糕状态。如果内部还没熟，就继续烤一会儿；如果已经烤好，就停止。真正有用的不是机械地执行"烤 30 分钟"，而是结合目标、步骤和观察结果决定是否继续。

这种循环也会带来风险：如果目标不明确、工具出错或停止条件设计不当，Agent 可能重复调用工具、浪费成本，甚至反复执行危险操作。因此，实际系统通常会设置最大步数、超时、预算、权限和停止规则。具体的内容我会在后面详细讲解。



#### 组成部分六：输出、日志与安全机制------让结果可交付、可追踪、可控制

输出模块负责把过程结果整理成用户能理解的形式。日志记录输入、工具调用、结果、错误和关键状态变化；安全机制则控制系统能够访问什么、哪些操作必须确认，以及遇到风险时如何停止。

**生活例子：**
旅行助理不能只说"安排好了"，而应告诉你哪些信息已查证、哪些酒店只是候选、哪些预订尚未完成。若它要付款，应该在付款前明确展示金额和对象，并要求授权。

这里顺便提一嘴：日志尤其重要。

用户报告"Agent 刚才删错文件了"，开发者需要知道它收到什么指令、看到了什么文件、调用了什么工具、工具实际执行了什么。没有可追踪记录，就很难定位问题。



### 1.1.4 为什么要把 Agent 设计成多个部分？

既然模型这么强，为什么不把所有东西都写进一个超长提示词（prompt），让模型自己完成一切？

因为现实任务不只是语言生成，还涉及实时信息、权限、状态、可靠执行和错误恢复。把职责分开，通常更容易维护和测试。

可以把它理解成一家餐厅：

-   厨师负责做菜，但不负责管理所有库存和收银系统。
-   服务员理解顾客需求、传递订单。
-   收银系统记录付款。
-   后厨流程规定菜品的制作顺序。
-   经理处理异常和顾客投诉。

如果让一个人只靠记忆完成所有工作，偶尔也能成功，但业务一复杂就容易出错。合理分工并不是为了让系统看起来复杂，而是为了让每一部分的职责更清楚。

常见的工程收益包括：

1.  **可替换**：可以换模型而不必重写所有工具。
2.  **可测试**：可以单独检查搜索工具是否准确、权限是否生效、停止条件是否合理。
3.  **可观察**：能看出错误发生在模型判断、工具执行还是状态管理环节。
4.  **可控**：能限制工具权限、调用次数、执行时间和成本。
5.  **可扩展**：需要新能力时，可以添加工具或模块，而不必把整个系统推倒重来。

当然，模块化也有代价：组件越多，接口、配置、日志和调试工作也可能越多。设计的目标不是"组件越多越好"，而是用足够简单的结构解决实际问题。



### 1.1.5 一个完整例子：让 Agent 帮你处理一份销售报表

假设你上传一份销售表格，并提出：

> "请分析本季度各地区销售情况，找出下降最明显的地区，核对数据后给我一份简短报告。不要修改原始文件。"

一个可能的 Agent 执行过程如下：

1.  **理解目标**：确定需要分析本季度、按地区汇总、比较变化、生成报告，并保护原始文件。
2.  **检查输入**：确认文件存在、字段含义清楚。如果"销售额"列不明确，先提问或查看说明。
3.  **选择工具**：使用文件读取工具获取表格，必要时用代码计算汇总与同比/环比。
4.  **执行计算**：按地区聚合数据，找出下降幅度最大的地区。
5.  **核验结果**：检查空值、重复行、日期范围、计算公式，必要时用另一种方式复核。
6.  **处理异常**：如果缺少上季度数据，不能假装算出了环比，应明确说明数据不足。
7.  **生成报告**：给出结论、关键数字、计算口径和局限。
8.  **交付与留痕**：保存新报告，不覆盖原文件，并记录使用了哪些数据和操作。

注意：其中有些步骤可以由固定程序完成，有些步骤可以交给模型动态决定。它们组合起来才构成完整的应用。Agent
并不意味着每个步骤都必须让模型自由发挥；在数据计算、权限校验和文件写入等环节，确定性的程序往往更可靠。



### 1.1.6 Agent 不是什么：四个常见误解

**误解一：只要接入了大模型，就是 Agent。**

不一定。一个只把用户问题发给模型、再把回答显示出来的程序，通常更像模型应用或聊天接口。它当然可能很有用，但不一定具有自主选择行动、使用工具和循环执行的能力。

**误解二：Agent 越自主越先进。**

不一定。自主性越高，系统可以处理的情况可能越多，但行为也更难预测，成本和风险也可能更高。对报销审核、医疗流程或财务操作而言，固定规则加人工审批可能比高度自主的 Agent 更合适。

**误解三：多 Agent 一定比单 Agent 强。**

不一定。多个 Agent 之间需要分工、传递上下文、协调结果，还可能重复工作或互相放大错误。只有当任务确实需要独立专业角色、并行探索或隔离权限时，多
Agent 才可能带来收益。

**误解四：模型说"完成了"，就代表任务完成了。**

不一定。系统应该依据可观察的证据判断是否完成，例如文件是否真实生成、邮件服务是否返回成功、数据库是否确认写入。语言上的承诺不是执行证据。



### 1.1.7 什么时候值得使用 Agent？

Agent 特别适合目标明确、但完成路径不完全固定的任务。例如：研究一个主题并根据资料补充检索、分析代码仓库并运行测试、根据业务情况查询多个系统后给出处理建议等。

如果任务很简单、规则固定、容错要求极高，传统程序或简单 Workflow 可能更合适。例如：每晚 12 点把某个文件复制到指定目录，没必要让模型临场决定怎么复制。

可以先问三个问题：

-   任务是否需要理解自然语言或处理非结构化信息？
-   执行过程是否需要根据中间结果调整下一步？
-   模型带来的灵活性，是否足以抵消额外的成本、延迟和风险？

如果答案有两个以上是否定的，那么建议先从简单方案开始。



**使用 Agent 不是目标，可靠地完成任务才是目标。**

## 1.2 Agent 的构建范式

"构建范式"可以理解为：**我们用什么样的组织方式，让模型和工具协同完成任务。**

它不是某个特定产品，也不一定对应一个固定的软件包，而是一种设计思路。

假设有一个简单任务："阅读一份用户投诉，判断问题类型，查询对应的处理规则，最后起草回复。"

这个任务可以有不同实现方式：可以按某种固定的流程步骤依次执行，也可以让模型根据投诉的内容自己设定处理步骤、是否需要补充信息等。两者都可能有价值，但适合的场景可能不同。



本节我们将讨论一下传统的/加入AI辅助的工作流（Workflow）范式和两种主流的智能体（Agent）范式。



### 1.2.1 Workflow 与 Agent：固定路线和动态决策

**Workflow（工作流）**
通常指由开发者预先设计好主要步骤和分支的执行流程。每一个具体的步骤可以是调用大模型处理基于自然语言的任务或非结构化数据，也可以调用普通程序完成预设的任务；关键是整体控制路线大体上已经由代码或配置确定下来。整个流程的结果是可预期的。

**Agent**（智能体）
通常指任务执行过程中，完全由大模型根据具体情况动态的决定下一步做什么、使用哪个工具，必要时调整策略。模型在一定范围自主实现了流程的控制。

一个实用的区分方法是问：**主要由谁决定下一步？**

-   如果主要由预先写好的程序决定，是 Workflow 范式。
-   如果模型根据当前任务和中间结果动态选择行动，是 Agent 范式。
-   也有很多生产系统介于两者之间：比如宏观模块层面上是固定流程，具体某些功能或者服务交给 Agent 灵活处理。反之亦然。



#### 生活例子：去医院看病

Workflow 范式就像去医院看病：取号、候诊、就诊、缴费、取药，每一步有清楚的规则和责任人，除了“就诊”那一步是医生根据实际病情给出不同的诊断外，其他所有的步骤都是固定和可预期的。

Agent 更像一个辅助就医的数字助理：先理解你描述的情况，再根据你提供的信息判断需要查询什么资料、整理哪些问题、提醒你准备哪些材料。如果出现无法判断的症状，它应该建议寻求专业人员，而不是无限制地自行决定。

两者并非对立。医院不会让智能助理自由改变缴费和处方权限；更合理的设计是用确定性流程守住边界，在需要理解与灵活处理的环节使用模型。



#### 对比表

| 纬度         | Workflow                         | Agent                                    |
| :----------- | :------------------------------- | :--------------------------------------- |
| 主要控制方式 | 预先定义的步骤、分支和规则       | 模型根据当前状态选择部分行动             |
| 可预测性     | 通常较高                         | 通常更灵活，但行为变化更大               |
| 处理意外情况 | 依赖预先设计的分支和异常处理     | 可以尝试调整策略，但也可能判断错误       |
| 调试难度     | 路径较固定，通常更容易复现       | 需要检查模型决策、上下文和工具轨迹       |
| 成本与延迟   | 常较容易估算                     | 可能因多轮决策和工具调用而增加           |
| 适用场景     | 重复、规则明确、审计要求高的流程 | 路径不固定、需要探索或根据反馈调整的任务 |



这张表表达的是常见倾向，不是绝对定律。Workflow 也可以有模型路由和动态分支；Agent 也可以受到严格的程序约束。



#### 常见 Workflow 模式

**1. 顺序执行（Prompt Chaining）**

把复杂任务拆成几个步骤，前一步的输出成为下一步的输入。

例子：先提取合同中的关键条款，再检查条款是否符合清单，最后生成摘要。每一步都有清楚的输入输出，便于定位问题。

**2. 路由（Routing）**

先判断输入属于哪一类，再送到不同处理路径。

例子：客服系统先判断用户问的是物流、退款还是产品使用，再调用对应流程。分类错误时可能走错路径，所以需要测试边界案例。

**3. 并行处理（Parallelization）**

把互相独立的子任务同时执行，再合并结果。

例子：分析一家公司的风险时，让系统分别整理财务、市场和舆情信息，最后汇总。并行可以缩短等待时间，但会增加协调与合并工作。

**4. 评估---优化（Evaluator--Optimizer）**

一个步骤生成初稿，另一个步骤按标准评估并提出修改，循环到达到要求或触及上限。

例子：先生成产品说明，再检查是否包含必要参数、是否超出字数、是否出现未经证实的承诺。评估器也会犯错，因此高风险内容仍应使用规则检查或人工审核。

**5. 分层协调（Hierarchical Workflow）**

由一个协调者把任务分派给多个子任务或专业模块，再汇总结果。

例子：研究助理把一份市场报告分成竞品、用户、价格三部分分别研究，再统一整理。这里的分工可以由固定程序安排，也可以由模型动态规划。



这些模式可以组合使用。重要的不是记住术语，而是理解每一种模式解决什么问题、增加了什么成本，以及如何判断它是否有效。Anthropic 的公开指南也强调，应从尽可能简单的组合模式开始，只在任务需要时增加 Agent 式的动态性。[参考：Anthropic《Building effective agents》](https://www.anthropic.com/engineering/building-effective-agents)



### 1.2.2 ReAct：思考、行动、观察，再继续

**ReAct** 是当前 Agent 开发的主要范式。它是 Reasoning（推理）与 Acting（行动）的组合名称。作为目前最常见的 Agent 设计思路，它强调让模型在行动过程中交替进行判断、调用工具和读取结果，而不是一开始就假定自己拥有完成任务所需的全部信息。

我们可以把它理解为"边查边做"的工作方式。

假设你问："明天下午去机场，几点出门比较稳妥？"

一个可能的 ReAct 流程：

1.  **思考**：需要知道航班起飞时间、机场、出发地和交通情况。
2.  **行动**：查询航班信息或请用户补充缺失信息。
3.  **观察**：工具返回起飞时间、机场位置或路况信息。
4.  **再思考**：发现明天下午可能拥堵，于是查询更早的交通方案。
5.  **再行动**：比较不同出发时间。
6.  **结束**：给出建议，并说明假设、缓冲时间和信息来源。

#### ReAct 的价值

-   **可以利用外部信息**：不必只依赖模型参数中学到的知识。**（调用外部工具）**
-   **可以根据结果改变路线**：如果第一次搜索没有结果，可以调整关键词或换工具。**（多次循环）**
-   **行动有机会被检查**：系统能在每一步验证工具是否成功、结果是否有用。**（反思）**
-   **适合路径不确定的任务**：下一步取决于当前发现，而不是所有步骤都能预先写死。



#### ReAct 的局限

-   **可能走弯路**：模型可能选错工具或使用不合适的搜索词。
-   **可能重复行动**：如果没有明确停止条件，可能反复查询同一件事。
-   **成本和延迟可能增加**：每一轮模型调用和工具执行都需要时间与资源。
-   **工具结果不一定可靠**：网页内容可能过时，工具返回可能不完整，模型也可能误读结果。



#### 一个关键提醒：不要把 ReAct 等同于"必须展示模型的完整内心独白"

工程实现上需要记录的是：

- 可检查的行动依据
- 工具调用及其参数
- 观察结果和决策记录

系统可以记录"为什么选择这个工具"的简短摘要，而不需要向用户展示或保存模型全部内部推理文本。可观测性应服务于调试、审计和安全，不应把内部推理文本当成唯一或必需的证据。



### 1.2.3 Plan-and-Execute：先制定计划，再逐步执行

**Plan-and-Execute（规划---执行）**
是另一种常见模式。系统先把大任务拆成子任务，形成一个计划；然后执行计划中的步骤，并根据实际情况决定是否需要重新规划。

例如，你说："帮我研究三款适合小团队的项目管理软件，比较价格、权限、自动化功能，最后给出推荐。"

系统可以先制定计划：

1.  明确团队规模、预算和必需功能。
2.  选择三款候选产品。
3.  查阅官方定价和功能文档。
4.  按统一维度整理对比表。
5.  检查信息是否来自可靠来源。
6.  根据需求给出推荐和限制说明。

执行阶段逐项完成。如果发现某款产品的官方价格页无法访问，系统可以尝试官方帮助文档或明确标注价格尚未核实，而不是编造数字。



#### 为什么需要先规划？

复杂任务往往包含许多相互依赖的步骤。先列出计划，可以帮助系统识别遗漏、安排顺序、估算成本，也方便用户确认方向。

再说得直白一点，主要是为了规避 **ReAct 范式下可能会出现的“干着干着就忘了最初目标”的情况**。

**生活例子：**
搬家前先列出打包、预约车辆、通知物业、交接钥匙等事项，比当天临时想到什么做什么更稳妥。



#### 规划不应变成僵硬的承诺

真实环境会变化。计划是当前最合理的路线，不是不可更改的合同。执行时可能发现：

-   某一步不再必要；
-   缺少关键资料；
-   某个工具不可用；
-   新信息改变了优先级；
-   用户提出了新的限制条件。

因此，成熟的 Plan-and-Execute
系统通常需要"计划---执行---检查---必要时重新规划"的机制，而不是一次性生成长计划后机械执行到底。

此范式最核心的点就是：**每一次循环都可以根据初始目标和实际情况更新“计划”！**



#### Plan-and-Execute 的优点与局限

优点：

-   任务全貌更清晰；
-   便于检查步骤是否遗漏；
-   对长任务更容易进行进度管理；
-   可以让用户提前确认范围和优先级。

局限：

-   初始计划可能建立在错误假设上；
-   计划越长，后续偏离的机会越多；
-   规划本身会消耗模型调用和时间；
-   过度规划可能让简单任务变慢。

一个实用原则是：小任务直接做，复杂任务先规划；执行中遇到重要新信息时，再更新计划。



### 1.2.4 ReAct 与 Plan-and-Execute 如何选择？

二者并不是互斥的技术路线。Plan-and-Execute 强调"先把路线想清楚"，ReAct 强调"行动后根据观察继续判断"。这是它们两者之间的只要区别。

但是在工程实现上，我们完全可以在一个系统中设计先规划，再在每一步执行时使用 ReAct 式循环。



下面我列举了一下实际的任务案例，以及它们适合的模式。大家感受一下：

| 场景                             | 更适合的起点                          | 原因                           |
| -------------------------------- | ------------------------------------- | ------------------------------ |
| 查询一个简单的事实               | 直接回答或一次工具调用                | 没有必要设计执行计划           |
| 根据实时路况决定出发时间         | ReAct 风格                            | 后续行动依赖查到的实时结果     |
| 完成多阶段的竞品研究报告         | Plan-and-Execute 并在步骤中使用 ReAct | 需要整体计划，也需要边查边修正 |
| 固定/不固定格式的数据导入        | Workflow                              | 规则明确，优先保证可预测性     |
| 涉及付款、删除、发送等高敏感操作 | 受控 Workflow + 必要的 Agent          | 灵活性不能取代权限和审批       |



### 1.2.5 其他常见构建范式

除了 ReAct 和 Plan-and-Execute，实际系统还会采用其他模式。下面这些名称并非互不相容的"流派"，它们常常可以拼装在一起。

#### 1. 工具调用（Tool Use / Function Calling）

模型根据任务选择一个已登记的工具，并按规定格式提供参数，由程序执行后把结果返回。

例子：用户问"我上个月一共花了多少餐饮费？"模型可以选择账单查询工具，并传入月份和类别。工具负责查询真实账单，模型负责理解请求、选择调用方式并解释结果。

工具调用是 Agent 的重要能力，但单次工具调用本身并不自动构成完整 Agent。系统还需要管理调用前后的状态、权限、失败与结束条件。

#### 2. 多 Agent 协作（Multi-Agent）

把复杂任务分给多个 Agent，可能由一个协调 Agent 分派任务，也可能让不同 Agent 负责独立角色。

例子：一个 Agent 整理财务数据，另一个研究市场变化，第三个负责审查报告中的来源与逻辑，最后由协调者汇总。

多 Agent 可能带来并行处理、专业分工和权限隔离，但也会引入协调成本、信息丢失、重复工作和错误传播。不要为了"看起来先进"而拆成很多 Agent；先确认单 Agent 或 Workflow 的瓶颈，再决定是否需要协作结构。

#### 3. 反思与自我修正（Reflection / Critique）

系统在生成结果后，再根据明确的标准检查自身输出，并尝试修正。

例子：生成一份会议纪要后，检查是否漏掉负责人、截止时间和待决事项。这个检查可以由同一个模型完成，也可以使用另一个模型或确定性规则来完成。

需要注意：模型自我检查不保证正确。若生成者和检查者依赖相似的错误假设，它们可能一起犯错。重要结论仍应通过原始数据、独立工具或人工核验。

#### 4. 检索增强生成（RAG）

**RAG（Retrieval-Augmented Generation，检索增强生成）**
指模型回答问题前，先从外部资料库检索相关内容，再根据检索结果组织回答。

例子：企业内部问答系统可能无法让模型凭训练知识回答"公司的报销标准是什么"，而是通过检索公司最新版报销制度，再引用对应条款回答。

RAG 是给模型补充外部知识的一种方法，并不必然意味着系统会自主规划或循环行动。它可以是普通问答应用中的一个环节，也可以成为 Agent 的一个工具。

知识库、检索和记忆的相关内容会在后续详细展开。

#### 5. 事件驱动与后台 Agent

有些任务不由用户每次即时发起，而是由事件或计划触发，例如收到新邮件、监控到异常指标、来自 Gitlab/Gerrit 的 webhooks、以及定时任务。

例子：系统每天检查库存，当某种商品低于阈值时提醒负责人。若只是固定阈值判断，普通自动化流程就足够；若需要结合多个来源判断异常原因，再决定查询哪些系统，Agent 能提供更灵活的分析能力。

后台运行需要额外考虑任务排队、取消、超时、重试、权限、资源上限和人工接管。能持续运行不代表应该无限制运行。



### 1.2.6 选择范式时，先从任务出发

面对一个真实的需求，不要一上来就问"应该用哪个 Agent 框架"，而应该先思考以下问题：

1.  **任务的成功标准是什么？** 结果怎样才算完成？
2.  **路径是否稳定？** 能否提前写清楚大部分步骤？
3.  **哪里需要模型判断？** 哪些步骤用普通代码更可靠？
4.  **需要哪些外部能力？** 搜索、数据库、文件、业务 API，还是代码执行？
5.  **失败后怎么办？** 能否重试、回滚、人工接管？
6.  **风险和成本有多高？** 是否需要审批、权限隔离和操作限额？
7.  **如何证明它有效？** 用哪些测试任务和指标判断改进是否真实？

建议从最简单的可行设计开始：先用程序完成确定性部分，把模型用于理解、分类、总结或必要的决策；只有当固定流程难以覆盖真实变化时，再增加
Agent 的动态决策能力。



注意：这里强调的是 Agent 的**”动态“**决策能力。

## 1.3 Harness 工程：模型之外的竞争力



### 1.3.1 为什么一个强模型，也可能做不好真实任务？

想象两个团队使用能力相近的模型开发编程助理。

团队 A 只提供一个输入框，把用户要求发给模型，再把生成的代码显示出来。模型写得不错，但它看不到完整项目结构，不能运行测试，也不知道文件是否保存成功。

团队 B 给模型提供项目文件读取、代码编辑、终端、测试运行、错误日志、版本控制和受限的执行环境。系统会记录每一步操作，允许模型根据测试结果修正代码，并在修改前后检查差异。

即使两边使用相近的模型，团队 B 也可能更容易完成真实开发任务。差异不仅来自模型，而来自模型周围的环境、工具、循环、状态、权限和反馈机制。

这些围绕模型组织起来、让它能够在真实环境中完成工作的工程设施，业界常用 **Harness** 来描述。可以把它理解成模型的"工作台、操作规程和运行环境"的组合。

DeepSeek Harness 的官方介绍使用了一个简洁表达：**Agent = Model + Harness**。

注意：这只是一个帮助理解系统分工的工程表达，而不是适用于所有学术定义的数学等式。[参考：DeepSeekHarness 官方介绍](https://www.deepseek.com/zh/harness/)



### 1.3.2 Harness 到底是什么？

在不同团队和产品中，Harness 的边界并不完全一致。广义上，它可以包含模型调用与循环控制、工具使用、上下文组装、会话和状态管理、执行环境、权限、安全策略、日志与评估等能力。具体产品可能只提供其中一部分，也可能把这些能力打包成完整的运行时。

可以用一张表理解它的常见组成：

| 工程能力       | 解决的问题                             | 生活化比喻                       |
| -------------- | -------------------------------------- | -------------------------------- |
| 模型适配与调用 | 如何向模型发起请求并处理响应           | 联系顾问的通信渠道               |
| Agent Loop     | 如何决定继续、调用工具或结束           | 工作流程的调度员                 |
| 工具注册与执行 | 模型能用哪些外部能力，如何实际执行     | 办公室里的打印机、电话和业务系统 |
| 上下文组装     | 当前这一步应该给模型看哪些信息         | 把当前任务需要的文件放在桌面上   |
| 会话与状态管理 | 如何延续任务、记录进度                 | 工作日志和项目看板               |
| 执行环境与沙箱 | 代码、命令和文件在哪里运行，权限有多大 | 有门禁的实验室                   |
| 权限与安全策略 | 哪些操作允许、哪些需要确认             | 印章、审批和钥匙管理             |
| 日志与追踪     | 发生了什么，如何定位问题               | 监控录像和操作记录               |
| 测试与评估     | 改动后是否真的好                       | 验收清单与质量检测               |



这不是每个 Harness 都必须遵循的固定清单，而是帮助开发者思考"模型周围还缺什么"的检查表。在实际项目中可以把这些能力放在框架里，也可以由应用开发者自行实现。



### 1.3.3 Harness 如何改变 Agent 的表现？

#### 1. 让模型看见正确的信息

模型无法自动告诉你它都需要些什么资料。Harness 需要决定在每一步把哪些用户要求、文件内容、历史记录、工具结果和规则提供给模型。

**例如：** 一个编程 Agent 如果只看到用户说"修复登录问题"，却看不到相关源代码、测试失败信息和项目约定，就只能猜。

若 Harness 能检索相关文件、运行测试并提供错误输出，模型就有了更可靠的工作基础。

#### 2. 让模型能够真正执行

模型生成"我需要读取并校验这个文件"这句话，但是它并不会真的自己去读取和检查文件。Harness 必须基于模型的回答转换成实际调用工具执行，并把结果返回给模型，并告诉模型，你要检查这个文件的内容，现在我把检查的结果告诉你。（在实际工程中，我们会要求模型以某种格式化的内容来请求调用工具，如 json、xml 等）

**例子：** 模型建议"把表格按地区汇总"，Harness 可以让它调用受控的 Python 环境或表格工具，而不是要求模型凭空算出数百行数据的结果。

#### 3. 让失败成为下一步的输入

在真实的工程任务场景中，模型很有可能会失败。Harness 可以把错误信息、测试结果和工具返回值再次交还给模型，让它修正参数、换一种方法或请求帮助。

**例子：** Agent 修改代码后运行测试，测试失败并指出某个函数缺少参数。系统把错误日志交给模型，模型据此修改代码并重新测试。若没有执行和反馈环节，模型可能只会给出一段"看起来正确"的代码。

#### 4. 让任务过程可追踪

Harness 可以记录模型输入、工具请求、工具结果、状态变化、错误与耗时，从而帮助开发者复现和分析失败。

**例子：** Agent 声称"邮件已发送"，但收件人没有收到。日志可以帮助确认它是没有调用邮件工具、还是工具执行失败，还是邮件服务返回成功但后续投递出了问题。

#### 5. 让行为受到约束

工具越强，风险越大。能读取文件的 Agent 可能读到不该读的内容；能执行命令的 Agent 可能运行危险命令；能发送邮件的 Agent 也可能编写一段 js 发出去。

Harness 可以通过最小权限、沙箱、命令白名单、敏感操作确认、超时和预算限制等方式缩小风险范围。模型自身的安全训练很重要，但不能替代系统层面的权限控制。



### 1.3.4 模型能力与系统能力：如何看待"模型之外的竞争力"？

一个实用的观察框架是把 Agent 的效果拆成几部分：

-   **模型能力**：理解、推理、生成、遵循指令的能力。
-   **信息质量**：给模型的上下文是否相关、准确、及时。
-   **工具能力**：能否访问正确系统，工具接口是否清晰可靠。
-   **执行控制**：是否能合理循环、重试、停止和恢复。
-   **环境与权限**：能否在安全、可复现的环境中完成操作。
-   **评估与迭代**：能否发现错误，并通过测试验证改进。

这些因素会相互影响，不能简单地用一个公式来评估最终的效果。但这个框架能帮助团队定位问题：当 Agent 表现不好时，不要一味更换更贵的模型；先查清它是否拿到了必要信息、是否有正确工具、是否能看到执行结果、是否设置了合适的停止条件。这里面的事儿多着呢！

**生活例子：**
再优秀的厨师，如果厨房没有合适的刀具、原料不新鲜、炉灶坏了，也很难稳定做出好菜。反过来，设备再好也不能完全替代厨师的技术和火候。模型和 Harness 的关系类似：两者共同决定实际表现。



### 1.3.5 Harness 与 Prompt、Agent 框架有什么区别？

这几个概念经常同时出现，但关注点不同。

-   **Prompt（提示词）**：告诉模型当前扮演的角色是什么、应该遵循什么规则、如何组织输出、如何使用工具。它是影响模型行为的重要输入。
-   **Agent 框架（Agent Framework）**：通常是帮助开发者构建 Agent 的软件库或开发框架，提供模型接口、工具调用、流程编排、状态管理等部分能力。
-   **Harness**：更强调让模型在具体环境里持续工作的整套支撑与控制机制，包括模型周围的工具、执行环境、循环、上下文、权限、状态、日志等。它可能由框架实现，也可能由多种组件共同构成。

三者有交集，不是严格互斥的类别。一个 Agent 框架可以提供 Harness 的一部分；一个产品也可能把提示词、框架和运行环境一起打包。

**比喻：** Prompt 像给员工的任务说明；Agent 框架像公司的流程模板和开发工具；Harness 更像整套工作环境、权限系统、操作流程、设备和记录机制。实际产品中，这些边界会重叠。



### 1.3.6 Harness 工程的核心思想

Harness Engineering（Harness 工程）不是简单地"给模型多接几个工具"，而是围绕模型在真实任务中的工作方式，系统性地设计和改进运行环境。它关注的问题包括：模型能看到什么、能做什么、如何得到反馈、何时继续或停止、如何恢复、如何追踪，以及怎样证明系统真的完成了任务。

可以归纳为六条实践原则。

**原则一：把任务拆成可验证的步骤。**

不要只要求 Agent"把项目做好"，而应让它知道如何检查结果。例如编程任务可以包含理解需求、修改代码、运行测试、检查差异和总结变更。

**原则二：为行动提供可靠反馈。**

工具应该返回明确结果或错误信息。能检查"文件是否存在"、"测试是否通过"，不要只依赖模型口头判断。

**原则三：让关键状态显式化。**

把目标、待办、已完成事项、阻塞原因和预算等记录在可检查的状态中，避免只靠越来越长的对话历史维持任务。

**原则四：权限与风险按操作分级。**

只读查询和不可逆写入不应该拥有相同的授权门槛。发送、付款、删除、发布等操作应根据风险设置确认、审批或限制。

**原则五：记录完整的执行轨迹。**

至少要能追踪重要输入、工具调用、返回结果、错误、状态变化和最终产物。记录要兼顾隐私与安全，不能为了追踪而无差别保存所有敏感数据。

**原则六：用真实任务持续评估。**

不要只看几次演示是否成功。建立覆盖常见任务、边界条件和失败案例的测试集，观察任务成功率、错误类型、成本、延迟和安全事件。改动后重新跑测试，避免"感觉更聪明了"却没有实际收益。



OpenAI 在关于 Harness Engineering 的工程分享中强调，当模型负责更多实际工作时，工程师的工作重心会转向环境、抽象、工具和约束的设计；遇到失败时，关键问题往往不是反复要求模型"再努力一点"，而是找出它缺少什么能力、信息或可执行的机制。[参考：OpenAI《Harness engineering》](https://openai.com/index/harness-engineering/)



### 1.3.7 DeepSeek Harness：一个具体的工程实例

在讨论 Harness 时，就不得不提到目前非常火的一个项目，它把抽象概念落到实处。

**DeepSeek Harness（简称 DSH）** 是 DeepSeek 推出的开源 Agent Harness 项目。根据其官方介绍，它面向日常工作、编码、资料研究和扩展 Agent
能力等场景，并采用"一切皆插件"的设计思路。截至本书资料核对时，官方仍将其描述为处于预览和持续迭代阶段，因此安装命令、插件接口和功能细节可能随版本变化。[官方介绍](https://www.deepseek.com/zh/harness/)；[GitHub 仓库](https://github.com/deepseek-ai/deepseek-harness)



#### "一切皆插件"是什么意思？

插件（Plugin）是可以独立添加、移除或替换的功能模块。DSH 的公开架构说明中，模型适配器、工具注册、会话日志、Agent 循环等能力都可以通过插件体系组合；其底层使用 Cordis 来管理插件、服务、事件和依赖关系。

**生活例子：**
想象一套模块化办公空间。你可以替换会议系统、文件柜、门禁和显示屏，而不必把整栋办公室拆掉重建。插件化架构希望达到类似效果：功能通过明确的接口协作，开发者可以按需求组合能力。

插件化的好处包括：

-   **可替换**：某项能力不合适时，可以替换对应模块。
-   **可扩展**：可以增加新的工具或界面能力。
-   **可组合**：不同任务可以使用不同能力组合。
-   **便于实验**：可以比较不同配置对实际任务的影响。

但插件化不意味着"随便安装都安全"。插件可能访问文件、网络或执行命令，必须检查来源、权限和代码行为。模块之间也需要兼容的接口与依赖管理。



#### 为什么运行轨迹很重要？

DSH的官方材料强调把模型在运行中看到和执行的关键事件写入会话日志，并提供轨迹查看、恢复、分叉、检索或回放等能力。不同版本的具体记录范围和界面可能变化，实际使用时应以对应版本的文档为准。

这反映了 Harness 工程的一个核心目标：**不只保存最后的答案，还要能够理解任务是怎样完成的。**

例如，编码 Agent 修改了一个文件后测试失败。通过运行轨迹，开发者可以查看它读取了哪些文件、执行了什么命令、测试返回了什么错误，以及后续如何处理。这样才能区分问题究竟来自模型判断、工具配置、环境依赖还是项目本身。



#### DSH 的运行模式能说明什么？

官方介绍列出多种运行模式，体现"按任务选择能力组合"的思路。例如，标准模式提供较完整的编码与研究工具；PTC 模式通过代码方式组合多步工具调用；极简模式则使用更少的工具来运行或测试 Agent；创造模式用于检查运行环境和试验插件等。

具体名称、能力范围和实现会随版本变化，读者应查看项目当前文档。[官方文档](https://deepseek-harness.github.io/deepseek-harness/en/reference/)

这些模式体现了一个重要工程思想：任务并不总是需要最大工具集。工具越多，模型能做的事可能越多，但选择空间、权限管理和调试复杂度也会增加。针对特定任务配置最合适的能力组合，往往比无差别地开放所有工具更稳妥。



#### 如何开始了解 DSH？

官方仓库给出的快速启动方式之一是使用 Node.js 运行：

``` bash
npx @deepseek-ai/dsh web
```

源码方式可参考项目仓库的最新安装说明：

``` bash
git clone https://github.com/deepseek-ai/deepseek-harness.git
```

仓库、依赖和命令可能变化；运行前请阅读当前版本的 README、开发文档与安全说明。尤其要注意：这类 Agent 运行环境可能接触本地文件、执行命令或访问互联网。建议先在专门的测试目录、虚拟机或容器中试用，不要直接授予不必要的系统权限。[GitHub 仓库与运行说明](https://github.com/deepseek-ai/deepseek-harness/)；[安全使用建议](https://www.deepseek.com/harness/privacy/)

本书此处介绍 DSH，是为了说明 Harness 的工程思想，而不是要求读者必须选择这个项目。学习重点应该放在可迁移的设计原则：插件化、明确的能力边界、执行轨迹、状态管理、可控权限和可验证的任务完成。



### 1.3.8 怎样评估 Harness 是否真的有用？

不能因为系统拥有更多工具、更多插件或更复杂的架构，就认定它更强。判断 Harness 是否有效，需要把它放到真实任务中比较。

建议至少观察以下维度：

| 评估为度   | 要回答的问题                       | 示例指标                             |
| ---------- | ---------------------------------- | ------------------------------------ |
| 任务成功率 | 最终产物是否满足要求？             | 一组任务中成功完成的比例             |
| 结果质量   | 结果是否准确、完整、符合格式？     | 专家评分、规则校验通过率             |
| 工具可靠性 | 工具是否被正确选择和调用？         | 调用成功率、参数错误率               |
| 恢复能力   | 失败后能否合理重试或改用其他方法？ | 故障恢复率、重复失败次数             |
| 效率       | 完成任务用了多少资源？             | 平均耗时、模型调用次数、工具调用次数 |
| 安全性     | 是否发生越权或未授权操作？         | 越权测试通过率、未授权操作次数       |
| 可追踪性   | 能否定位失败原因？                 | 关键时间覆盖率、复现成功率           |



比较时应尽量保持任务集、模型版本、工具权限和成功标准一致。如果同时换了模型、提示词、工具和 Harness，就很难知道提升来自哪里。可以逐项修改并重复测试，逐步识别真正有效的改动。

关于评估的详细方法，会在本书后续的 Agent 性能评估部分进一步展开。

## 本章小结

读完这一部分，请记住以下几点：

1. **Agent 不等于 LLM 模型，而是模型与运行系统的协作。**
   模型负责理解和判断，工具负责执行，状态与上下文帮助系统接续任务，控制循环决定继续、调整还是结束。

2. **Workflow 与 Agent 的关键区别，是主要由谁决定执行路径。** 

   Workflow 的路线通常由程序预先定义；Agent 会让模型根据当前情况动态选择部分行动。现实系统经常把两者结合起来。

3. **ReAct 范式强调行动与观察的循环，Plan-and-Execute 范式强调整体规划与分步执行。**
   两者可以组合，选择取决于任务复杂度和路径是否可预先确定。

4. **并非所有任务都需要 Agent。**
   简单、固定、可预测的任务通常更适合普通程序或 Workflow。只有当灵活决策确实有价值时，才值得引入更多自主性。

5. **Harness 是模型周围的工程支撑体系。**
   它可以涉及工具、上下文、状态、执行环境、权限、循环控制、日志与评估。好的 Harness 应当让模型能够安全、可靠、可追踪地完成任务。

6. **模型的口头承诺不等于任务已经完成。**
   完成状态应该由文件、系统返回值、测试结果或其他可观察证据确认。

7. **复杂不等于先进。** 

   多 Agent 协作、更多插件和更长的计划都会带来成本。先从最简单的可行方案开始，再用真实任务和可重复测试证明是否需要增加复杂度。

   

## 自测题

建议先不看前文，尝试回答以下问题。

1.  为什么"能够生成答案"不等于"能够完成任务"？
2.  模型、工具、上下文、状态和控制循环分别承担什么职责？
3.  如果一个系统按固定步骤处理退款申请，其中只有分类环节使用大模型，它更接近 Workflow、Agent，还是二者结合？为什么？
4.  ReAct 和 Plan-and-Execute 各自最关注什么？它们能否同时出现在一个系统里？
5.  为什么工具调用成功后，Agent 仍然需要检查返回结果？
6.  Harness 为什么不仅是提示词，也不仅是一个工具列表？
7.  如果 Agent 经常把代码改错，应该如何判断问题来自模型、上下文、工具、环境还是评估方式？
8.  对一个会删除文件或发送邮件的 Agent，为什么必须设计权限与确认机制？

### 参考答案要点

1.  生成答案是语言输出；完成任务还可能需要查询真实信息、执行操作、处理失败并验证结果。
2.  模型负责理解和判断；工具提供外部能力；上下文提供当前可见信息；状态表示任务进展；控制循环决定下一步与停止条件。
3.  通常是 Workflow 与模型能力结合的混合系统，因为整体步骤固定，但分类环节使用模型判断。
4.  ReAct 强调判断---行动---观察的迭代；Plan-and-Execute 强调整体规划后逐步执行。可以先规划，再在各步骤中使用 ReAct。
5.  工具可能报错、返回不完整数据或执行了与预期不同的操作；必须根据结果决定下一步。
6.  Harness 还涉及执行环境、工具调度、上下文与状态管理、权限、日志、恢复和评估等工程机制。
7.  查看执行轨迹，分别检查输入信息、模型决策、工具参数与返回、环境状态、测试标准，并通过控制变量的对比实验定位问题。
8.  因为这些操作可能造成真实且不可逆的影响。最小权限、操作限额和人工确认可以降低错误与越权风险。
